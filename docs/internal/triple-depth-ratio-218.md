# triple の深さ比（issue #218 Phase 1・実測ログ）

完成済み triple の 3 主構成点は、ネックラインからの深さ（`top: peak − nlAvg` /
`bottom: nlAvg − valley`）が**互いにどれだけ違ってよいかを一度も検査されていない**。
[issue #218](https://github.com/tjackiet/bitbank-lab-mcp/issues/218) Phase 1 として、
その深さ比（`max(depth) / min(depth)`）の分布・分母の退化・H&S 系との二重出力を測る。

**本ログは計測のみで、リポジトリのコードは 1 行も変更していない。**
hard gate を入れるか / 閾値 / 分母ガードの値 / 価格基準は **Phase 1 では決定しない。**

計測対象は **`price`（終値）基準と `extremePrice`（高安）基準の 2 つだけ**。
triple のネックラインは `nlAvg`（中間 2 点の終値平均）を両端の `y` に置いた**水平線**
（`detect_triples.ts:363-365` / `:584-585` / `:796-797` / `:989-990`）で、
`findBreakoutIdx` にも同じスカラーを渡している。**線として評価しても値が変わらない**ので、
issue #216 / #211 の「スカラーか線か」の軸は triple には存在しない
（[0-1 章](#0-1-ネックラインが水平であることの検算)で全件検算した）。

## 結論（計測結果の要約。対策の決定は含まない）

1. **母集団が薄い。深さ比の議論に使える構造は、価格系列上でわずか 13 件しかない。**
   940 ケースで完成済み triple の生の行数は 256、構造単位（系列, tf, type, 構成点 idx）は 37、
   **tf ラベルを畳んだ価格系列上の構造は 13**（合成 4 + 実データ B 9。**実データ A は
   完成済み triple が 1 件も出ない**）。検出器が組み立てた候補まで広げても
   価格系列上 32 構造。**「分布に空白帯がある」を根拠に閾値を非任意と言える母数ではない**
   （[1-1 章](#1-1-4-段階の件数) / [6-3 章](#6-3-空白帯を支えているものの特定)）。
2. **relaxed 2 経路（`:719` / `:919`）は本コーパスで 1 行も出さない。** 到達はしている
   （`*_relaxed` の棄却が 5,682 行）が accepted は 0。**本ログの実測はすべて strict 2 経路
   （`:287` / `:513`）のもの**である（[0-3 章](#0-3-完成済み-4-経路のうち-2-つは-0-件)）。
3. **分母は退化していない——`price` 基準では。** `accepted` 候補 341 行で
   `min(depth) / パターン高さ` の最小は **19.78%**、p25 66.16% / p50 77.76% で、
   issue #210 の `MIN_TARGET_DISTANCE_HEIGHT_RATIO = 0.15` を下回るものは **0 件**。
   `1min` / `5min` でも最小 19.78% / 36.61% で小さくならない。
   **#210 と同型の分母ガードを `price` 基準で置くと no-op になる**
   （[2 章](#2-計測-2-分母の分布)）。
4. **退化は「分母が小さくなる」ではなく「点がネックラインの反対側へ抜ける」形で出る。**
   `price` 基準で `depth ≤ 0` の点は 108 行 / 構造単位 14 件で、**全件が第3構成点**
   （第1・第2構成点は 0 件）。これは #216 の記載値と全桁一致する。
   `extremePrice` 基準ではこの 14 構造が `depth > 0` に戻るが、
   **`depth(extreme) ≥ depth(price)` が常に成り立つ**ため反対側が消えるだけで、
   `min/height` が 1.58%、深さ比が **96.07** というゼロ近傍の分母に化ける。
   **価格基準の選択は「件数がいくつになるか」ではなく「退化がどちらの形で出るか」を決める**
   （[0-2 章](#0-2-depth--0-の分離) / [2-4 章](#2-4-price-基準で-depth--0-だった構造は-extremeprice-基準でどこへ行くか)）。
5. **二重出力は実在する。構造単位で 18 ペア（共有 3 点 5 / 2 点 6 / 1 点 7）。**
   `globalDedup` 後に同じ case で共存し、うち 35 ペア（延べ）は両方が `data.patterns` に出る。
   issue が挙げた実例（triple の谷2・谷3 が逆 H&S の頭・右肩と一致）は
   `realB|1hour|triple_bottom|242-249-272` ↔ `inverse_head_and_shoulders|230-232-249-265-272`
   として再現し、**同じ 3 谷を主構成点にする逆 H&S（`230-236-249-265-272`、共有 3 点）も
   別に存在する**（[3 章](#3-計測-3-二重出力)）。
6. **比の大きい triple はほぼ全件、点を共有する H&S が実際に出ている。**
   深さ比 ≥ 2.0 の triple 構造 12 件のうち 11 件（91.7%）に共有 H&S があり、
   ≥ 2.5 では 6/6（100%）。対照として比 < 1.5 の 8 件では 0 件。
   **ただしこの数字は 13 の価格系列構造から出ているので、割合として読むこと**
   （[4 章](#4-計測-4-厳格化しても取りこぼさないか)）。
7. **時間足別テーブルは本コーパスでは分布の比較にならない。**
   標準コーパスの「時間足」は**リサンプリングではなくパラメータのラベル**なので、
   同じ価格系列に別の tf を与えてもローソク足は 1 本も変わらない。実測でも
   **13 構造中 12 件で深さ比は tf を跨いで完全に同一**（残り 1 件が割れるのは tf ではなく
   `swingDepth` 差で中間点が変わったため）。tf 軸が動かしているのは
   **どの構造がゲートを通るかという選択だけ**で、「分足はスイング点がノイジー」は
   本コーパスでは検証できない。#198 の轍を踏まないよう、
   **時間足別テーブルは「選択効果の表」として読むこと**（[5 章](#5-計測-5-比は時間足で揃っているか)）。
8. **閾値の非任意性は「見かけ上ある」が、支えているのは深さ比ではなく既存ゲート。**
   `accepted` プール（構造単位 106。うち比を計算できる 84 構造）では
   1.5 / 2.0 / 2.5 / 3.0 のいずれも ±0.01 で通過集合が動かず、
   0.1 以上の空白帯が 9 本ある。**しかしゲートを外したプール（844 構造 / 価格系列上 122 構造）
   では 1.5・2.5・3.0 で通過集合が動く**（+0.01 で −2 / −22 / −4）。空白帯を作っているのは
   `pattern_too_small` / `*_too_shallow` / `neckline_slope_excess` / 構造ゲート /
   `validateLevelSpread` が高い比の候補を先に落としているからで、
   **#215 で `MIN_CONFIDENCE` の空白帯が崩れたのと同じ壊れ方をする**
   （[6-3 章](#6-3-空白帯を支えているものの特定)）。

### 測る量の定義

- **深さ**: `top: depth_i = peak_i − nlAvg` / `bottom: depth_i = nlAvg − valley_i`。
  `nlAvg` は検出器が出力した `neckline[0].y`（= `neckline[1].y`）。
- **深さ比**: `max(depth) / min(depth)`。理想は 1.0、下限は定義上 1.0。
- **価格基準**: `price`（終値。同水準判定・ネックラインの慣行）と
  `extremePrice`（高安。値幅の慣行）の**両方**。#216 の `LevelSpreadMetrics` の表と同じ 2 系統。
- **パターン高さ**: `heightProj` = `|主構成点 3 点の平均 − ネックライン|`。
  **`buildTripleScore` の `patternHeight` そのもの**で、`breakoutQuality` 軸が使っている高さ。
  `depth` の相加平均に一致するので、`min(depth) / heightProj ≤ 1` が定義から従う
  （検算: 全 256 行で不一致 0）。
- **`depth ≤ 0` の扱い**: ネックラインの反対側にある点は #216 の対象なので、
  比が負・無限大にならないよう**主分布から外して別集計にする**（[0-2 章](#0-2-depth--0-の分離)）。

## 0. 前提の検算

### 0-1. ネックラインが水平であることの検算

完成済み 4 経路が出した **256 行すべてで `neckline[0].y === neckline[1].y`**（不一致 0 行）。
また `depth` の相加平均が検出器の `patternHeight`（`buildTripleScore` の
`avgLevel − necklinePrice`）と一致することも 256 行全件で確認した（不一致 0 行）。

中間 2 点（`top` なら 2 谷 / `bottom` なら 2 山）は出力の `pivots` に載らないので
検出器と同じ手順（区間内の最安 / 最高）で再構成した。**再構成した 2 点の終値平均が
出力のネックラインと一致することを 256 行全件で検算**（再構成できなかった行 0 / 不一致 0）。
issue #216 が完成済み 4,833 行に対して行ったのと同じ検算で、結果も同じく不一致 0。

| `price` 基準の分類 | 構造 | `extreme` 深さ比 p50 | max | `extreme` `min/height` p50 | min |
|---|---:|---:|---:|---:|---:|

| `depth > 0` | 23 | 2.38 | 3.73 | 65.01% | 47.74% |

### 2-5. 深さ比を実際に縛っているもの（`validateLevelSpread` との関係）

`validateLevelSpread`（`structural.ts`）は
`spreadRatio = spreadAbs / heightAmp ≤ MAX_LEVEL_SPREAD_RATIO(0.5)` を hard gate にしている。
`spreadAbs` は主構成点 3 点の**終値**の max−min で、これは `price` 基準の
`max(depth) − min(depth)` と同一の量。したがって

```text
ratio = max(d)/min(d) = 1 + spreadAbs / min(d)
min(d) ≥ max(d) − 0.5·heightAmp
⇒ ratio ≤ 1 / (1 − 0.5·heightAmp/max(d))      （右辺の分母が正のとき）
```

**この上界は `price` 基準にしか当たらない**——`extremePrice` 基準の depth 差は `spreadAbs` とは
別の量なので、実測でも上界を超える（`triple_top` の `extreme` p50 15.63 > 上界 p50 5.52）。

`price` 基準での実測:

| type | n | `spreadRatio` p50 | 同 max | `heightAmp/max(d)` p50 | 解析上界 p50 | 実測 ratio p50 |
|---|---:|---:|---:|---:|---:|---:|
| `triple_top` | 7 | 0.04 | 0.33 | 1.50 | 4.00 | 1.06 |
| `triple_bottom` | 16 | 0.35 | 0.41 | 1.65 | 5.64 | 2.40 |

**上界は緩い**（4.00〜5.64 に対し実測 1.06〜2.40）。`accepted` の `spreadRatio` は
最大 0.45 で上限 0.5 に張り付いていない。一方 `MAX_LEVEL_SPREAD_RATIO` が実際に落としている
候補（`peak_spread_vs_height_excess` / `valley_spread_vs_height_excess`）は
**構造単位 37 件すべてが深さ比 5.0 以上**（min 5.41 / p50 8.03 / max 325.08、
そのときの `spreadRatio` は 0.53〜0.76）。

**つまり `MAX_LEVEL_SPREAD_RATIO` は「深さ比が極端な候補」を落としてはいるが、
本 issue が対象にする 1.5〜4.0 の帯には 1 件も効いていない**（落としている 37 構造は全件 5.0 以上）。
その帯を実際に削っているのはサイズ検査・ネックライン傾き・構造ゲートのほうで、
どれも深さ比を直接見てはいない（[6-3 章](#6-3-空白帯を支えているものの特定)）。

## 5. 計測 5: 比は時間足で揃っているか

**先に結論**: 深さ比は定義上スケールフリーだが、**本コーパスでは「実測の分布が時間足で揃っているか」
という問い自体が測定できない。** 標準コーパスの「時間足」は**リサンプリングではなく
パラメータのラベル**（#205 / #216 / #211 の同名の注記と同じ限界）で、
`realB` に `1min` を与えても `4hour` を与えても**ローソク足は同じ 365 本のまま**である。
tf が変えるのは `tolerancePct` / `minBarsBetweenSwings` / `swingDepth` の既定値と
`getSizeThresholdsForTf` / `getHeadProminenceForTf` の閾値、つまり**どの構造がゲートを通るか**だけ。

| `synth buildRectangleRangeCandles / triple_bottom 4-10-16` | `1day`, `1hour` | 1.11 |
| `realB triple_top 204-219-236` | `4hour`, `1hour`, `1min`, `5min`, `15min`, `30min` | —（`depth ≤ 0`） |
| `realB triple_top 219-223-232` | `4hour`, `1hour`, `1min`, `5min`, `15min`, `30min` | —（`depth ≤ 0`） |
| `realB triple_top 219-236-257` | `4hour`, `1hour` | 2.32 |
| `realB triple_top 257-265-275` | `1hour` | 1.79 |

同じ `1hour` の中で `swingDepth` が変わると中間 2 点（谷間の山）が別のピボットになり、
ネックライン `nlAvg` が動くため。

### 5-2. したがって時間足別テーブルは「選択効果の表」である

| 層 | tf | n（構造単位） | p50 | p90 | max |
|---|---|---:|---:|---:|---:|
| 合成 | `1hour` | 4 | 1.03 | 1.09 | 1.11 |
| 合成 | `1day` | 4 | 1.03 | 1.09 | 1.11 |
| 実データ B | `1min` | 3 | 2.66 | 3.71 | 3.97 |
| 実データ B | `5min` | 2 | 2.53 | 2.63 | 2.66 |
| 実データ B | `15min` | 2 | 2.53 | 2.63 | 2.66 |
| 実データ B | `30min` | 2 | 2.53 | 2.63 | 2.66 |
| 実データ B | `1hour` | 5 | 2.35 | 2.55 | 2.66 |

**合成（1.00〜1.11）と実データ B（1.79〜3.97）の差は tf ではなく系列の差**である。
実データ B の中では `1min` の p90 / max だけが高いが、これは
**`1min` でしか `77-86-100`（比 3.97）が通らない**ことによる 1 構造の出入りで、
「分足はスイング点がノイジー」の証拠にはならない——`1min` の閾値
（`getSizeThresholdsForTf` の `heightPct 0.0008 / depthPct 0.0013`）が最も緩いので、
**同じ 365 本の中でより小さい構造まで拾えるようになるという選択効果**である。
実測でも `77-86-100` は **`5min` / `15min` / `30min` / `1hour` では `peak_too_shallow`、
`4hour` 以上では `pattern_too_small`** で落ちており、落とす検査は `getSizeThresholdsForTf` の
時間足別テーブル（`1min` の `depthPct 0.0013` vs `5min` の `0.0029`）である。
この構造は分母（`min(depth)/height` = 43.12%）が本コーパスで最小でもある。

**時間足でのノイズ差を測りたいなら、同一区間の実際の 1 分足・5 分足を新たに凍結する必要がある。**
本コーパスにはその材料が無い。#198 は理由を確かめずに時間足別テーブルを流用した事故なので、
**本ログの[2-2 章](#2-2-時間足別price-基準構造単位)と本章の表は「選択効果の表」としてのみ引くこと。**

  `accepted` の上端（10.25）はこの定数が決めている。
- `neckline_slope_excess`（`NECKLINE_SLOPE_LIMIT = 0.02`）が p50 2.67 の候補を 693 行落としている。
- 構造ゲート（`neckline_*_pre_decline_*` / `no_neckline_cross_*` / `retracement_out_of_band`）が

上のゲート群が凍結されていることを前提に置く必要がある**——そしてそれは前提として置けない
（`getSizeThresholdsForTf` は #152 で、`MAX_LEVEL_SPREAD_RATIO` は #138 / #178 で動いている）。

## 7. Phase 2 に持ち越す論点（決定はしない）

1. **価格基準を先に決める。** `price` 基準は分母が退化せず、代わりに第3構成点が
   ネックラインの反対側へ抜ける（#216 の領域）。`extremePrice` 基準は反対側を消す代わりに
   分母が 1.58% まで退化する。**同じ 14 構造に対する診断が基準で入れ替わる**ので、
   閾値・分母ガードはどちらを採るか決めた後でしか議論できない。
2. **#216 との境界を決める。** `depth ≤ 0` は本 issue の集計から外したが、
   両 issue が同じ 14 構造を別の名前で扱っている。gate を 2 本立てるのか
   1 本にまとめるのかは #216 Phase 2 と揃えて決める必要がある。
3. **分母ガードは `price` 基準では no-op。** #210 の 0.15 を移植しても本コーパスでは 1 件も動かない
   （最小 19.78%）。置くなら `extremePrice` 基準か、閾値を 0.2 以上にする根拠が要る。
4. **閾値の非任意性は主張できない。** [6-3 章](#6-3-空白帯を支えているものの特定)のとおり
   空白帯は既存ゲートの副作用で、母集団も価格系列上 32 構造しかない。
5. **母集団を増やす手当てが要る。** 実データ A（`1day`）には完成済み triple が 1 件も無く、
   実データ B の 9 構造 + 合成 4 構造が全母集団。実際の 1 分足・5 分足を凍結すれば
   [5 章](#5-計測-5-比は時間足で揃っているか)の「時間足でノイズが変わるか」も測れるようになる。

## 9. 母集団の限界

本ログの数字を引くときに必ず併せて読む必要がある制約:

5. **ネイティブ錨は実質 1 系統。** 実データ A × `1day` に triple が無いため、

## 計測の再現手順

計測用のハーネスはリポジトリに含めない（`docs/internal/` の他の計測ログと同じ）。
再現するには以下を組む:

1. `tests/detect_patterns_fixtures.test.ts` の 22 個の `build*Candles()` を抜き出す。
2. `tools/detect_patterns.ts` の `resolveParams` → `detectSwingPoints` → `DetectContext` 構築 →
   6 検出器（doubles / H&S / triangles / wedges / pennants / triples の順）→ `globalDedup` →
   ライフサイクル絞り込み、をそのままの順序で呼ぶ。
   `analyzeIndicators` は経由せず fixture の candle 配列を直接渡す（`pastBuffer` は 0）。
3. 940 ケースを[計測条件](#計測条件)の組み合わせで回す。
   **補助スイープ 44 のオプションは既定 1 通り**（`includeForming: false` /
   `includeCompleted: true` / `includeInvalid: false`）——ここを全部入りにすると
   issue #206 / #213 の検算値がずれる。
4. `type` が `triple_top` / `triple_bottom` かつ `status` が `completed` / `near_completion`、
   `pivots` が 3 点の行を集め、`neckline[0].y` を `nlAvg` として depth を計算する。
5. ゲート無効プールは `ctx.debugCandidates` から集める
   （`accepted` + [6-3 章 (b)](#6-3-空白帯を支えているものの特定) の棄却理由。
   中間 2 点は検出器と同じ手順で再構成し、その終値平均がネックラインと一致することを検算する）。

[ハーネスの検算](#ハーネスの検算205--206--207--213-の数値の再現)の 12 項目 +
issue #216 の 6 項目が一致すれば、組み方は本ログと同じである。
