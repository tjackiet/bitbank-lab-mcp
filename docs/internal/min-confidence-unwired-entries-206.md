# `MIN_CONFIDENCE` の未配線 4 エントリ（issue #206・実測ログ）

`tools/patterns/config.ts` の `MIN_CONFIDENCE` は 6 種別ぶんのエントリを持っていたが、
**読まれていたのは `triple_top` / `triple_bottom` の 2 つだけ**だった。
[issue #206](https://github.com/tjackiet/bitbank-lab-mcp/issues/206) の Phase 1（計測）と
Phase 2（判断・実装）のログ。

## 結論（断定）

1. **A（4 エントリを配線する）は採らない。** #199 が triple に 0.6 を置いた根拠 3 つのうち
   **2 つは type 非依存で成り立つが、3 つ目（`FORMING_MAX_CONFIDENCE = 0.59` との隣接）は
   triple 固有**で、H&S / double では成り立たない（[4 章](#4-06-という値の位置づけ)）。
   さらに実測で、**triple の 0.6 を非任意にしていた 2 つの性質**——分布に空白帯がある・
   切られる集合が 1 つのクラスに収まる——が **H&S にはどちらも無い**（[2 章](#2-a-の影響)）。
2. **D（triple の下限も外す）も採らない。** 外すと #199 が根拠付きで消した 2 構造が
   そのまま戻る（[3 章](#3-d-の影響)）。対称性のために根拠のある判断を巻き戻すことになる。
3. **B（4 エントリを削除して「下限を持つのは triple だけ」を docstring に明記）を採った。**
   `data.patterns` は 940 ケース全件で完全一致（[5 章](#5-b-の検証)）。
4. **#207 の docstring が主張していた「18 件は 1 つのクラス」は今も成り立つ。**
   現行 0.6 が切る triple 候補は構造単位 15 / 価格系列上 3 構造で、
   **全件が `retracement ≤ 0.1905` かつ全件が未ブレイク**、`levelMargin` は 0.5858〜0.9391
   とばらける（#207 の記載と一致）。

### A / D は post-hoc のフィルタでは測れない

出力を confidence で後から間引いても、実際にゲートを入れた場合と**別の結果になる**:

- **relaxed フォールバックが発火する。** `detectHeadAndShoulders` / `detectDoubles` /
  `detectTriples` はいずれも「strict が対象 type を 1 件も見つけなかったとき」にだけ
  relaxed 段へ落ちる。ゲートで strict の唯一の検出が消えると `found = false` になり、
  **post-hoc では出てこないパターンが出る。**
- **`globalDedup` の代表が入れ替わる。** 畳み込みは逐次で、勝者は
  `statusScore` → `confidence` → `range.end` の順に選ばれる。低い候補が先に消えると
  別の候補が代表になり、`range` が変わってその後の重なり判定まで変わる（#213 の 3-2 と同じ性質）。

そこで **`detect_hs.ts` / `detect_doubles.ts` に実際にゲートを入れて測った**
（triple と同じ配置＝ブレイク検出・高さ算出の後、パターン構築の直前。
理由コードも triple と同じ `confidence_below_min`）。閾値を実行時に差し替えて
0 / 0.6 / 0.65 / 0.7 を振っている。**閾値 0 のゲートが 940 ケース全件で変更前と
バイト単位で一致する**ことを先に確認してあるので、以下の差分は閾値だけの効果。

### D を採る場合に連鎖する問題

`FORMING_MAX_CONFIDENCE = 0.59`（`detect_triples.ts`）の docstring は根拠を

## 4. 0.6 という値の位置づけ

#199 が 0.6 を採った根拠は 3 つ。**H&S / double で成り立つのは 2 つだけ。**

| # | 根拠 | 実装 | H&S / double でも成り立つか |
|---|---|---|---|
| 1 | 低 confidence 警告ラベルの境界 `confidence < 0.6` | `detectPatternsViewsHandler.formatPatternLine` | **成り立つ**（type 非依存の分岐） |
| 2 | LLM に出す整合度の帯「0.6 未満 = 形状不十分」 | `detectPatternsViewsHandler` の `trustNote`（detailed / full 両方） | **成り立つ**（type 非依存の文言） |
| 3 | 形成中の上限 `FORMING_MAX_CONFIDENCE = 0.59` との隣接 | `detect_triples.ts` のローカル定数 | **成り立たない**（triple にしか無い） |

3 の実測（構造単位）:

| type | forming の n | forming の min | forming の max | 0.6 以上の forming |
|---|---:|---:|---:|---:|
| `triple_top` | 4 | 0.59 | **0.59** | **0** |
| `triple_bottom` | 3 | 0.59 | **0.59** | **0** |
| `head_and_shoulders` | 6 | 0.50 | **0.78** | **2** |
| `inverse_head_and_shoulders` | 6 | 0.84 | **0.87** | **6** |
| `double_bottom` | 3 | 0.93 | **1.00** | **3** |

triple は上限 0.59 に張り付くので、完成済みの下限を 0.6 にすると
**forming ≤ 0.59 / completed ≥ 0.60 で帯が重ならない**。
H&S / double の forming にはその上限が無く、`double_bottom` は 1.00 まで出る。
**「0.6 を境に status が決まる」という triple の性質は他 type に無い**ので、
「0.6 は既にこのリポジトリにある線だから」という論法はそのままでは使えない。

なお 1 / 2 が成り立つということは、**下限を置かなくても LLM は「形状不十分」を受け取る**
ということでもある。実測では現行の出力に `confidence < 0.6` の
`head_and_shoulders` が延べ 4 件 / `inverse_head_and_shoulders` が延べ 4 件あり、
いずれも警告ラベル付きで出ている。

## 6. 併走の制約

**#211（`necklineAt` の外挿クランプ）とは併走していない。** #211 案 B はブレイク検出を変えて
`breakoutIdx` → `status` → `duration` → `confidence` と連鎖するため、A / D を採った場合の効果と混ざる。
B は挙動を変えないので実際には衝突しないが、Phase 1 の計測値（特に 2 章の閾値スイープ）は
#211 の前の値である点に注意。

## 7. 積み残し

- **`FORMING_MAX_CONFIDENCE = 0.59` の根拠は triple の 0.6 に依存したまま。** B では
  `MIN_CONFIDENCE.triple_*` を残したので破綻していないが、将来 triple の下限を動かすなら
  この定数も一緒に見ること。
- **`double_*` の下限は「置いても no-op」ではなく「知見が無い」。** 本コーパスの
  `double_top` / `double_bottom` は構造単位で 6 / 14 件しか無く、最小値もそれぞれ 0.73 / 0.65。
  **標準コーパスに double の低整合度サンプルが無いだけ**で、「double には低整合度が出ない」ことは
  実測できていない。double を厚くしたコーパスが手に入ったら再評価する余地がある。
- **`head_and_shoulders` の 0.42〜0.59 帯（構造単位 33 + 72 件）は出力に残る。**
  `globalDedup` を通ると延べ 8 件まで減り、いずれも低 confidence 警告ラベル付き。
  「ラベルで足りるか」は LLM 側の挙動の問題なので、実運用のログで再確認する余地がある。
