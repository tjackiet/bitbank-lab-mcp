# relaxed フォールバックの過剰緩和（issue #227・実測ログ）

[issue #227](https://github.com/tjackiet/bitbank-lab-mcp/issues/227) の Phase 1（計測）と
Phase 2（判断・実装）のログ。`detect_hs.ts` の `RELAXED_FACTORS`（段1 `x1.6_0.6` / 段2 `x2.0_0.4`）が
実データで過剰緩和になっていないかを測り、4 択から 1 つを選ぶまで。

> **本ログは Phase 1 の 2 回目の計測。** 1 回目（PR #232）は標準コーパス 800 ＋ 実データ B 96 で
> relaxed accepted が**全項目 0 件**になり、issue 本文のライブ実例を再現できなかった。
> 原因は実例が実データ B（`btc_jpy_1hour_2026_08`、2026-08-12〜08-28）の**期間の外**にあったこと。
> 本ログは新 fixture（実データ C）を足して測り直したもの。

## 結論（断定）

1. **relaxed の発火可否を決めているのは窓の左端（= `limit`）であって、期間だけではない。**
   同じ実データ C でも、窓長 120（左端 `2026-08-30T14:00Z`）では `head_and_shoulders` の
   strict 0 件率が 100.0% で段2 が accepted になるのに対し、**窓長 150 以上では strict 0 件率が
   0.0%** で relaxed は評価すらされない（[2 章](#2-計測-1--3-段別-accepted-と-strict-0-件の頻度)）。
   実データ B が 0 件だったのは期間の違いだけでなくこれが理由で、**同じ系列でも `limit` 次第で発火する**。
2. **issue 本文のライブ実例を fixture 上で完全に再現した。** 段2 `relaxed_hs_x2.0_0.4` /
   構成点の窓ローカル idx `[29, 36, 39, 43, 48]` / 頭の突出 **0.484%**（strict 要求 0.83% の 58%）/
   整合度 **0.79** が本文の記載と全項目一致（[1 章](#1-ライブ実例の再現)）。
3. **膝は無い。** 段2 の係数 `head` を 0.30〜0.58 で動かしても通過集合は**完全に一定**で、
   0.59 で 0 に落ちる。ただしこれは「ゼロから離れた集団」ではなく**標本 1 点によるステップ**で、
   `0.4` の非恣意性の根拠にはならない（#214 の非恣意性テストの意味では**不合格**）。
   段2 が拾った唯一の頭は、段1 のゲート（比 0.6）を **0.017 下回っただけ**
   （[3 章](#3-計測-2-段2-でのみ拾われた構造の頭の突出)）。
4. **段1 は一度も accepted にならない。** 標準コーパス 800 ＋ 実データ B 96 ＋ 実データ C 96 ＋
   窓長スイープ 256（呼び出し 2,496 回）を通じて段1 accepted は **0 件**。`× 0.95` のペナルティを
   段別にする案（選択肢 3）は**効果を測る母数が無い**ため見送った。
5. **Phase 2 は選択肢 2（`headProminence` 軸を strict の閾値で採点する）を採った。**
   ゲートは緩いまま、点数だけ正直にする。膝が無い以上「段2 を削る」（選択肢 1）根拠が無く、
   一方で論点 1（緩めたことが整合度に反映されない）は実データで裏が取れたため
   （[5 章](#5-phase-2-の判断)）。
6. **`data.patterns` は件数が 1 件も動かない。** 1,248 ケースを全フィールド突き合わせて、
   動くのは実データ C の窓長スイープの `head_and_shoulders`（`relaxed_hs_x2.0_0.4`）**24 行の
   `confidence` と `scoreComponents` だけ**（[6 章](#6-datapatterns-への影響)）。

## 3. 計測 2: 段2 でのみ拾われた構造の頭の突出

段2 accepted は延べ 24 件 / 構造 2 件。**2 件とも頭は同じ**（fixture idx 284）で、右肩だけが違う。

### 段2 の係数 `head` を動かしたときの通過集合

| `head` | H&S 発火（組 / 延べ） | 構造 | 通る構造の比 min | 前段との差 |
|---:|---:|---:|---:|---|
| 0.30 〜 0.58 | 3 / 24 | 2 | 0.583 | **全域で変化なし** |
| 0.59 | 0 / 0 | 0 | — | H&S −3 |
| 0.60 | 0 / 0 | 0 | — | ±0 |

**「膝がある」とは読めない。** 0.30〜0.58 で完全に平ら、0.59 で 0 に落ちるのは、
通過している構造が**実質 1 つ（頭が同一）**だからで、比 0.583 の上下でステップになっているだけ。
#214 の非恣意性テストが要求する「ゼロから離れた集団」は観測できていない。

段2 の頭ゲート手前まで通る 5 点窓の `突出率 ÷ strict gate` を 0.05 刻みで見ても、
**段2 のゲート 0.4 と段1 のゲート 0.6 の間に落ちる窓は 0.583 の 1 つだけ**:

| 比の区間 | realC H&S | realC 逆H&S |
|---|---:|---:|
| [0.10, 0.15) | 16 | 18 |
| [0.15, 0.55) | **0** | **0** |
| [0.55, 0.60) | 21 | 0 |
| [0.60, 0.75) | 0 | 0 |
| [0.75, 0.80) | 9 | 0 |
| ≥ 1.00 | 12 | 0 |

`0.4` は**空区間の中**に置かれている。動かしても何も変わらないという意味では安定だが、
それは「この位置でなければならない」根拠ではない（空区間のどこでも同じ）。

## 4. 計測 4: `headProminence` 軸を strict の閾値で採点し直す試算

`buildHsScore` に渡す `headProminenceGate` は、strict では `headProminencePct`、relaxed では
**`headProminencePct × factors.head`** だった。つまり `headProminence` 軸は**緩めた側の閾値に
対する余裕**を採点していた。strict のゲートで採点し直すと:

| 系列（窓） | 5 点 idx | 比 | headProminence 現行 | 同 strict 採点 | conf 現行 | conf strict 採点 | Δ |
|---|---|---:|---:|---:|---:|---:|---:|
| `@last120` | 29-36-39-43-48 | 0.583 | 0.3135 | 0.0000 | 0.79 | 0.73 | **−0.06** |
| `@last120` | 29-36-39-43-45 | 0.583 | 0.3135 | 0.0000 | 0.74 | 0.68 | **−0.06** |

**突出が strict の要求に届いていないのに 0.3135 点が入っていた。** strict のゲートで測れば
`clamp01(1 − gate / prominence)` が負になり 0 点に落ちる。

論点 1 の**逆転**も陽性対照で観測できた。合成 fixture に `headProminencePct` を明示して
strict を落とすと、同じ構造が段1 で拾われたときの conf **0.65** に対し、より緩い段2 で
拾われたときは **0.66**——**緩い段で拾われたほうが高い点数**になっていた。
strict 固定で採点すると両方 **0.62** に揃う。

## 5. Phase 2 の判断

issue 本文の 4 択と実測の対応:

| 選択肢 | 採否 | 理由 |
|---|---|---|
| 1. 段2（`head: 0.4`）を削る | **却下** | 膝が無い（[3 章](#3-計測-2-段2-でのみ拾われた構造の頭の突出)）。段2 が拾った唯一の頭は段1 のゲートを 0.017 下回っただけで、削る根拠が「たまたま 0.583 だった」以上に無い。標本 1 点で通過集合を変える不可逆な仕様変更はしない |
| **2. `headProminence` 軸を strict の閾値で採点する** | **採用** | 論点 1 が実データで裏取りできた（[4 章](#4-計測-4-headprominence-軸を-strict-の閾値で採点し直す試算)）。**ゲートを変えないので通過集合が不変**で、回帰リスクが最小。膝が見つかれば後から選択肢 1 を足せる（排他ではない） |
| 3. `× 0.95` のペナルティを段別にする | **見送り** | 段1 accepted が 2,496 呼び出しで 0 件。**段別にする効果を測る母数が無い** |
| 4. 何もしない | **却下** | ライブ実例が再現でき、`headProminence` 軸に 0.3135 点が誤って入っていることが実測で確定したため |

### 実装

`tools/patterns/detect_hs.ts` の relaxed 完成済み 2 経路（H&S / 逆 H&S）で、
`buildHsScore` に渡す `headProminenceGate` を `headProminencePct * factors.head` から
**`headProminencePct`**（strict のゲート）に変えた。**ゲート判定（`factors.head` を掛ける側）は
触っていない。**

## 6. `data.patterns` への影響

6 検出器 → `globalDedup` → ライフサイクル絞り込み → 型間排他（#218）→ `rankPatterns` まで通し、
**1,248 ケースの `data.patterns` 相当を配列まるごと**（rank 順・全フィールド）突き合わせた。

| 指標 | 値 |
|---|---|
| ケース総数 | 1,248 |
| `data.patterns` 完全一致のケース | **1,236** |
| 差分があるケース | 12 |
| **件数が変わったケース** | **0**（延べ 4,070 → 4,070。追加 0 / 削除 0） |
| type × コーパスの件数差 | **0 組**（全 53 組） |
| 動いたフィールド | **`confidence` と `scoreComponents` のみ** |

動いた行の内訳:

| コーパス | type | 経路 | 行数 |
|---|---|---|---:|
| 実データ C 窓長スイープ | `head_and_shoulders` | `relaxed_hs_x2.0_0.4` | **24** |
| 合成 / 実データ A / 実データ B / 実データ C（365 本） | 全 type | 全経路 | **0** |

件数が動かないのは、**ゲートを変えていない**ことに加え、H&S 系には `MIN_CONFIDENCE` が
配線されていない（#206 で `triple_*` 以外の 4 エントリを削除した）ため confidence で切られないから。
`FORMING_MIN_CONFIDENCE`（0.5）は形成中経路のもので、今回触った完成済み relaxed 経路には掛からない。

`tests/fixtures/detect_patterns_1hour_data_patterns_baseline.json` は**更新していない**
（実データ B が対象で、含まれる H&S 系 4 件は**すべて strict 経路**。回帰テストは無改変で通る）。

## 補遺: 実データ C を足しても標準コーパスが 0 件のままである理由

実データ C を「365 本を 1 窓」で渡すと、実データ B と同じく段1 / 段2 とも 0 件になる。
relaxed が通らないのは頭の突出ではなく**窓の形**で、relaxed は**連続する 5 ピボット**しか
見ない（strict は `enumerateHsWindows` で非連続の組も見る）。窓を広げるほど間に別のピボットが
挟まり、5 点が連続しなくなる。窓長 120 で発火したのは、その窓では 5 点がちょうど連続したため。

**この経路は `limit` に強く依存する。** 標準コーパスが `limit` を 1 つしか持たないかぎり、
relaxed の実害は「たまたまその窓長で測ったか」に左右される——`limit` を軸として掃かないと
評価できない、というのが本計測で得られた方法論上の教訓（#219 の「プールしない」と同じ種類の話）。
