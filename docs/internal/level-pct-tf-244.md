# 同水準判定（価格相対 3 つ）の時間足追従の実測（issue #244 Phase 1）

`scripts/measure_level_pct_tf_244.ts` の出力をそのまま貼ったもの（§9）に、
補正した問題設定（§3）と Phase 2 への推奨（§7）を足したメモ。
**検出器・`config.ts`・`structural.ts` は 1 行も変更していない。**

候補ビルド（ablation）は `tools/patterns/` を一時領域へディレクトリごと展開し、
`structural.ts` の `DOUBLE_LEVEL_MAX_PCT` / `HS_SHOULDER_MAX_PCT` の**数値リテラルだけ**を
差し替えた複製で、作業ツリーには触れていない。`tolerancePct` は検出器の外（`DetectContext`）から
渡る値なのでソースは触らず ctx で差し替える。

## 1. 読み方

- **「同水準判定の実測値」**は、その検出器の同水準ゲートが実際に見ている量。
  - double: `relDiff(peak1.price, peak2.price)`（終値基準。`near` / `isSameLevel` と同じ量）
  - triple: 3 山（3 谷）の pairwise `relDiff` の**最大**（検出器は 3 組すべてに `near` を掛ける）
  - H&S: `relDiff(p0.price, p4.price)`（左右肩）
- **`spreadRatio`** = 主構成点のばらつき ÷ パターン高さ（`levelSpreadMetrics`）。**無次元**。
  H&S では算出しない——#178 項目 3 のとおり肩は `heightAbs` の端点にならないので比が意味を持たない。
- **「律速」** = その構造にとって**先に上限へ当たる側**。使用率 `実測 ÷ 上限` が大きいほうを律速とする
  （価格相対の上限はその経路の実効閾値、高さ相対の上限は `MAX_LEVEL_SPREAD_RATIO = 0.5`）。
- **ATR 換算** = `実測値 ÷ その時間足の ATR`。ATR は 1day 実測 2.75% に #152 の ATR 比を掛けたもの
  （`1hour` は 0.57% で実測と一致）。
- **候補テーブル** = `getSizeThresholdsForTf` と同じ ATR 比を 3 つのアンカー（0.03 / 0.05 / 0.04）に
  掛けただけのもの。**`tolerancePct` の `1day` 以上だけは現行の tf-auto 値を据え置く**
  （アンカー 0.04 を機械的に当てると `1week` 3.5% → 4% / `1month` 3% → 4% と**緩む**方向になり、
  #152 の約束 2 と本 issue の「締める方向」の両方に反する）。
- **落ちる件数は 2 通り出す。**
  - **静的判定**（issue の指定）: 今 accepted な構造の実測値を候補閾値と比べるだけ。
  - **ablation**（裏取り）: 候補ビルドを実際に走らせた accepted 構造数の before / after。
    差が出るのは同水準判定**以外**への波及があるとき（§5）。
- **構造** = `(系列, 時間足, type, 構成点 idx)` で畳んだ単位。オプション 8 通りと、同じピボット列を
  生む `swingDepth` の重複を除く。
- 「時間足」は**パラメータ組の名前で再サンプリングではない**（#211 / #216 / #242 / #243 / #249 と
  同じコーパスの組み方）。
- コーパスは**プールしない**（#219）。**時間足別の結論は実データ B / C / D（実 1hour 365 本）と
  実データ A の 1day だけから出す**（#178。標準コーパスの実データ A 96 は同じ 1day 90 本に `tf`
  ラベルを付け替えたもので、時間足別の内訳は独立系列ではない）。標準コーパスは参考値。
- 実データ C の**窓長スイープ 256**（末尾 60〜365 本）を別建てで足してある。**relaxed が実際に
  発火する唯一の設定**（窓長 120）が #227 の再計測で分かっているため、これを入れないと計測 3 の
  before / after が全部「0 → 0」になる。

## 3. 補正した問題設定

issue 本文は「同水準判定が固定パーセンテージで時間足に追従していない」と書いているが、
**高さ相対の無次元ゲートが既に入っている**ので、正確にはこう:

| 判定 | 基準 | 時間足追従 | 適用先 |
|---|---|---|---|
| `validateLevelSpread` / `validateLevelDiff`（`MAX_LEVEL_SPREAD_RATIO = 0.5`） | 構成点の差 ÷ パターン高さ | **無次元なので不要** | double / triple（完成済み） |
| `DOUBLE_LEVEL_MAX_PCT = 0.03` | 価格相対 | **固定** | double |
| `HS_SHOULDER_MAX_PCT = 0.05` | 価格相対 | **固定** | H&S の肩（＋窓生成の `outerShoulderOk`） |
| `tolerancePct`（`getDefaultToleranceForTf`） | 価格相対 | 1day 4% / **1hour 5% / 15min 6%**（短いほど緩い） | double / triple / H&S（＋ triple の `confidence` 採点） |

つまり本 issue の対象は**価格相対の 3 つ**。H&S は #178 項目 3 の結論（肩は `heightAbs` の端点に
ならないので高さ相対の比が意味を持たない）により価格相対しか使えず、**H&S の肩の同水準判定が
時間足で実質機能していない**という issue の見立ては実測でも支持された（結論 4）。

double / triple は高さ相対ゲートが既に効いているので「価格相対の上限を締めても出力が変わらない
可能性がある」というのが Phase 1 の事前予想だったが、**実測では変わる**（結論 3）。理由は簡単で、
候補テーブルが価格相対の絶対値を 1/5 近くまで下げるため、実データ 1hour の
`spreadRatio ≈ 0.36`（高さ相対の使用率 0.73）でも価格相対の使用率が 1 を超えるから。
**「今は高さ相対が律速」と「締めても出力が変わらない」は別のこと。**

## 4. 発見元ケースの位置（実データ D / `double_top 329-334-338`）

| | 値 |
|---|---|
| 山1 終値（idx 329） | 12,718,980 |
| 山2 終値（idx 338） | 12,639,245 |
| `relDiff` | **0.627%**（1.10 ATR） |
| `spreadRatio` | 0.363（高さ相対の使用率 0.727） |
| 現行の実効閾値（`min(tolerancePct 5%, DOUBLE_LEVEL_MAX_PCT 3%)`） | 3.000% |
| 候補の実効閾値（`min(0.830%, 0.620%)`） | **0.620%** |
| 判定 | **落ちる**（超過 0.007 ポイント） |

issue 本文の「1hour 向けに ATR 比で換算すると閾値は 0.6% 前後になり、この 2 点は紙一重になる」は
**そのとおりで、しかも落ちる側**。ただし本タスクの前提「#242 で既に `invalid` なので出力は
変わらない」は**部分的に誤り**——`swingDepth` auto / 2 / 3 では `invalid` だが、
**`swingDepth=6` では `completed`（accepted）**で、候補テーブルはこの出力を実際に消す。

紙一重であること自体が結論 10（非恣意性の不合格）の一番強い実例でもある。
**この type / 時間足の accepted 分布はこの 1 点しかなく、閾値はその 0.007 ポイント下にある。**

## 5. 同水準判定以外への波及（Phase 2 で必ず切り分けが要る）

ablation で消えた構造のうち、静的判定（同水準の実測値 > 候補閾値）では説明できないものが
標準コーパスに 2 件あった。**3 閾値のどちら側だけを動かすと消えるか**をスクリプト内で切り分けてある。

| 構造 | 候補ビルドでの棄却理由 | `tolerancePct` だけ | 2 定数だけ | 原因 |
|---|---|---|---|---|
| `completed_triple_top` / 1hour / `5-9-14-18-23`（肩 0.763% < 候補 0.830%） | `confidence_below_min` | **消える** | 残る | **`tolerancePct` が triple の `confidence` の採点軸に入っている。** 締めると `MIN_CONFIDENCE.triple_* = 0.6` を割る |
| `btc_jpy_1day_2026` / 4hour / `20-24-27-53-80`（肩 1.228% < 候補 2.040%） | （候補に現れない） | 残る | **消える** | **`HS_SHOULDER_MAX_PCT` は `outerShoulderOk`（`enumerateHsWindows`）でも使う。** 締めると外側の肩が「明確に超える」判定になり、**窓自体が生成されない** |

どちらも `HS_SHOULDER_MAX_PCT` / `getDefaultToleranceForTf` の docstring に書いてある既知の
第 2 の役割だが、**「同水準判定の閾値を時間足別にする」という言い方だけでは見落とす。**
Phase 2 で 3 閾値のどれかを動かすなら、この 2 経路を分けて設計するか、少なくとも差分の帰属に使うこと。

## 7. Phase 2 への推奨（決定はしない）

### 推奨: **`HS_SHOULDER_MAX_PCT` だけを時間足別にする案を主、「何もしない」を次点**

根拠は 4 つ。

1. **H&S の肩には高さ相対の受け皿が無い**（#178 項目 3）。double / triple は
   `MAX_LEVEL_SPREAD_RATIO` が無次元の hard gate として既に入っていて、実データ 1hour では
   **そちらが律速**（結論 2）。**「時間足に追従していない判定」が本当に露出しているのは H&S だけ。**
2. **効き先が最大。** 実データ 1hour の accepted な逆 H&S の 1/3〜1/2（B 5/14・C 4/10・D 5/11）が
   落ちる。肩 `relDiff` 2.4〜2.7%（4.3〜4.8 ATR）の構造群で、**1 時間足で「同水準の肩」と
   呼ぶには広すぎる**という issue の主張がそのまま当たる集合。
3. **`tolerancePct` は 3 つの中で最も動かしてはいけない。** 公開スキーマパラメータであり、
   同水準判定以外に triple の `confidence` 採点軸（§5）・forming の倍率・`near` を使う
   他検出器にも入っている。tf-auto 表を締めると副作用が本 issue の範囲外に広がる
   （#198 の「時間足別テーブルの無検証流用で事故になった前例」と同じ形になりうる）。
4. **`DOUBLE_LEVEL_MAX_PCT` を締める積極的な理由が実測から出てこない。** 実データ 1hour の
   double は高さ相対律速で、価格相対の使用率は 0.209。締めると発見元ケースのように
   **0.007 ポイント差で切る恣意的な線**になる（結論 9 / 10）。

### `HS_SHOULDER_MAX_PCT` を時間足別にするときに残る宿題

- **窓生成（`outerShoulderOk`）と肩ゲートを分けるか決める。** §5 のとおり同じ定数が
  2 つの仕事をしており、締めると窓生成側の効果（窓が消える）が肩ゲート側の効果（肩で落ちる）と
  混ざる。分けるなら `HS_SHOULDER_MAX_PCT`（肩ゲート）と `HS_OUTER_SHOULDER_MAX_PCT`（窓生成、
  現行値据え置き）に割る案。**分けないなら、`view=debug` の理由コードでは
  「窓に現れない」としか見えない**ことを docstring に書くこと。
- **非恣意性は主張できない**（結論 10）。#214 の基準では不合格なので、
  `HS_SHOULDER_MAX_PCT` の docstring に現在ある ablation 表（0.15 / 0.10 / 0.05 / 0.02 / 0.01）と
  同じ形で「値はつまみ」であることを明記する。`MIN_CONFIDENCE` の ⚠️ 節と同じ扱い。
- **`4hour` 以降は実測ではない**（`getSizeThresholdsForTf` / `getHeadProminenceForTf` と同じ限界）。
  ATR 比が √t 推定なのでそのまま引き継ぐ。

### 「何もしない」を次点に置く理由

実データ 3 系列で消えるのが逆 H&S 14 構造中 5 件で、**そのうち目視で「肩と呼べない」ことを
確認した構造は 1 つも無い**（本 Phase では目視判定をしていない）。#249 が案 D（何もしない）を
採ったのと同じ形——**落ちる集合が「構造として失格」であることを示せていないうちは、
検出を減らす変更を入れない**。Phase 2 で入れるなら、落ちる 5 構造の目視判定を先にやること。

### #249 案 C は本 issue に混ぜない

落ちるのは実データ B の 1 構造だけ（結論 12）で、#249 Phase 1 の結果から動いていない。
**1 件のために完成済み経路へ新しい上限を足す根拠にはならない。** 本 issue は
「価格相対 3 つの時間足対応」に閉じ、案 C は #249 側で改めて判断する。

## 8. #178 項目 1（形成中 triple の levelSpread）との関係

同じ族の問題だが**本 issue の対象外**。#178 項目 1 は「完成済み triple には高さ相対の
`validateLevelSpread` が入ったのに、形成中 triple の同水準判定は `tolerancePct ×
FORMING_*_FACTOR` の価格相対のままで、高さ相対の受け皿が無い」というもので、
**基準の不統一（価格相対のみ vs 価格相対 AND 高さ相対）**を指している。本 issue は
価格相対の閾値自体を時間足別にする話で、軸が違う。

ただし**接点が 1 つある**——形成中 triple の同水準判定は `tolerancePct` を分母に持つので、
本 issue で `tolerancePct` の tf-auto 表を締める案（推奨では採らない）を採ると、
**#178 項目 1 の未対応部分にも同時に効いてしまう**。形成中の分布は本 Phase では測っていない
（計測対象は accepted な完成済みのみ）ので、`tolerancePct` を動かす案を検討するなら
issue #178 項目 1 側の計測が先に要る。逆に `HS_SHOULDER_MAX_PCT` だけを動かす推奨案なら接点は無い。
