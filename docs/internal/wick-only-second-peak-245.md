## 1. 読み方

- **見ているのは `data.patterns` 相当の出力集合だけ。** 検出器内のフックも `tools/patterns/` の
  展開も無い（#243 の計測と同じ流儀）。issue #245 が問うているのは「**accepted に混ざるか**」で、
  内部の候補を数えても材料にならない。縮小段（検出 → `globalDedup` → ライフサイクル絞り込み →
  `excludeTriplesSharingHsMainPoints`）はスクリプトの `runPipeline` が本体
  （`tools/detect_patterns.ts`）と同じ順序で再現する。

- **`includeForming` / `includeInvalid` は全ケースで true。** `near_completion` は
  `includeForming` が要り（#270）、§5 の「その後」の追跡は `invalid` / `expired` を見る。
  178 が固定窓で回していたオプション 8 通りは回していない（ライフサイクル絞り込みの手前の
  集合を見ないので、8 通りは同じ候補を 8 回数えるだけ）。**ケースの並びは 178 と同じまま**にして
  ケース数の単位（12,104）を揃えてある。

- **3 つの数え方を混ぜない。**

  | 単位 | 定義 | 使いどころ |
  |---|---|---|
  | 延べ | accepted な出力 1 件を 1 | ゲートの発火率 |
  | 実体 | `時間足 + type + 主構成点の ISO 時刻` で畳む | 178 / 262 / 268 と比較するとき |
  | **値動き** | **時間足ラベルまで落として** `type + 主構成点の ISO 時刻` で畳む | **目視で見る形の数**（#262 §8-1 と同じ） |

  実データ B / C / D は実 1 時間足 365 本に `1day` / `4hour` / `1hour` のラベルを付け替えて回して
  いるので、同じ形が実体として 2〜3 回数えられる。**「何個の形があるか」は値動きで言う。**

- **`4hour` 行の 0 は「4 時間足では出ない」ではない。** 時間足別の内訳は**ローソク足そのものが
  実データである組**だけを母集団にしている（実データ B / C / D の `1hour` と実データ A の `1day`。
  #178 の注意）。実 4 時間足の系列はコーパスに無いので `4hour` は構造的に常に 0 になる。

- **写した検出器定数は本物を神託にして検算している。** `BREAKOUT_BUFFER_PCT`（0.015）と
  `MAX_BARS_FROM_EXTREMUM`（20）は `detect_doubles.ts` の module-local な `const` で export されて
  いない。本 Phase は検出器を触らない（#245「やらないこと」）ので export を足さず写しで済ませ、
  代わりに **`completed` な double が申告する `breakoutBarIndex` と、写しで再導出した最初の
  ブレイク足が一致するか**を全ケースで検算している（§10 §0 の「食い違い 0 件」）。

- **自己検算が先に走る。** issue #245 本文の発端の形（実データ D の `limit=72` 窓 / `swingDepth: 6`）で
  `closeGap` 0.099 / `wickShare` 0.733 / `heightAbs` 219,423 を再現できなければ、**数字を 1 つも
  出す前に例外**になる。

## 2. 結論（計測結果の要約。対策の決定は含まない）

1. **#245 が残していた問い（「ヒゲだけの山2 の直後に、再上昇せずそのまま割る形」）に該当する
   形は 12,104 ケースで 0 件。** 仮の閾値（`closeGap` ≤ 0.2 かつ `wickShare` ≥ 0.5）に当たったのは
   **値動き 1 つだけ**（延べ 85 / 実体 1）で、**それは issue #245 本文の発端の形そのもの**
   （`btc_jpy` / `1hour` / 山1 `2026-09-03T21:00Z` – 谷 `09-04T02:00Z` – 山2 `09-04T06:00Z`）。
   **新しい形は 1 つも出ていない。**

2. **その 1 件の 3 値判定は「保留」**（正当な failed retest 0 / 呼べない 0 / 保留 1）。
   山2 の翌足以降にネックラインは割っている（実データ C の idx 363）が、**割る前に終値
   12,711,037 まで戻して山2 の終値 12,639,245 を越えている**——#242 が `peak_after_last_pivot` で
   落としたのと同じ値動きで、failed retest とは呼べない。

3. **つまり accepted に混ざっているのは「別の形」ではなく、#242 の形が経路ゲートを
   すり抜けたもの。** すり抜けの機構は 2 つで、**どちらも既知かつ意図された挙動**:

   | 機構 | 中身 | 既存の扱い |
   |---|---|---|
   | 深さ依存 | `swingDepth: 6` では再上昇の足（実データ D の idx 343 / 高安 12,731,234）が極値にならない（前後 6 本に 12,750,000 と 12,800,000 がある）ので経路上のピボットが消える | **#251 案 3 で仕様として固定**（`tests/patterns/breakout-path-double.test.ts`） |
   | 窓の端 | `detectSwingPoints` は前後 `swingDepth` 本を要求するので、**窓の終端から `swingDepth` 本の中にある足はピボットになれない**。実データ C の 365 本窓（終端 idx 364）では再上昇の足 idx 362 が `swingDepth: 3` のときこの余白に入り、ピボットになれない | 明文化されていない（本 Phase の副産物） |

   ローリング窓の追跡が同じことを言う。`swingDepth: 6` は end=344 以降 **20 窓連続で `completed`**、
   `swingDepth: 2 / 3 / auto` は窓が伸びると `invalid` に落ちる（§5 の一覧）。**`swingDepth: 2` の
   実データ C では end=364 でも `invalid`**——idx 362 が深さ 2 ならピボットになるため。

4. **分布は「終値でも山がある」側に寄っている。** accepted double は延べ 1,151 / 実体 30 /
   **値動き 19**。`closeGap` は値動き単位で min 0.030 / p50 0.415 / max 0.741、`wickShare` は
   min 0.072 / p50 0.232 / max 0.733。**`closeGap` ≤ 0.2 の値動きは 4 つ、`wickShare` ≥ 0.5 の
   値動きは 2 つで、両方に当たるのは発端の形だけ。**

   もう 1 つの `wickShare` ≥ 0.5（0.544）も **#242 系の形**——実データ C の `double_top`
   174-177-184 で、これは #242 の回帰テストが `peak_after_last_pivot` で落ちることを固定して
   いる構造そのもの（ここでは短い窓でまだブレイクしておらず `near_completion` で出ている）。
   **accepted な母集団で `wickShare` が上位 2 つの形は、両方とも #242 が対象にしている値動き。**

5. **仮の閾値 0.2 / 0.5 は空白帯の中に無い。** 値動き単位の最も広い空白帯は
   `closeGap` が 0.415〜0.538（幅 0.123）、`wickShare` が 0.544〜0.733（幅 0.189）。
   どちらも仮の閾値から離れている。加えて**値動きは 19 しか無い**ので、
   そもそも帯の広さを非恣意性の根拠にできない（#214 の基準。§4-5）。
   **「0.2 / 0.5 の非恣意性は主張しない」**——該当が 1 件に絞れたのは分布の谷を当てたからではない。

6. **`closeGap` > 0 は既存ゲートの帰結。** `validateMainPointsNecklineSide` は top で
   `necklinePrice − 山.price >= 0` を落とすので、**「終値では山が完全に無い（ネックラインと同値か
   下）」形は既に accepted に入らない。** 残っているのは「わずかに上」の帯で、その厚みが
   §4 の `closeGap` の下側の分布そのもの。issue #245 の症状（終値がネックラインの 0.17% 上）は
   この帯の下端にある。

7. **既存ゲートとの重なりは 0 件で、`near_completion` のゲート集合は完成済みと同じ**（#270 の検算）。
   accepted double 1,151 件（`completed` 257 / `near_completion` 894）に `validateLevelDiff` と
   ネックライン側検査を静的に当てて、理由を返すものは **0 件**。accepted triple 6,105 件と
   accepted H&S 13,792 件でも 0 件。

8. **同族（triple の山3 / 谷3、H&S の右肩 `p4`）に該当は 0 件。** triple の `closeGap` は
   延べ全体で min 0.234（top）/ 0.154（bottom）、`wickShare` max 0.353（top）/ 0.246（bottom）。
   H&S は `closeGap` min 0.017 / `wickShare` max 0.236 だが、**#178 項目 3 のとおり
   `heightAbs` の端点は頭と谷で肩は端点にならない**ので、H&S の 2 量は参考値。

## 3. 問題設定（コードの事実）

### 3-1. 混合基準

反転系の検出器は 1 つの構造判定の中で 3 つの価格基準を使い分けている
（`swing.ts` の `Pivot` docstring が単一ソース）:

| 何を | 使う価格 | 根拠 |
|---|---|---|
| 極値判定（この足がスイングか） | `high` / `low` | `detectSwingPoints`。ヒゲ 1 本で極値が決まる |
| 同水準判定・ネックライン | **終値**（`Pivot.price`） | #131 / #132「水準同一性は終値」。ヒゲ 1 本で構造比較が動くのを避ける |
| パターン高さ（値幅の評価） | `high` / `low`（`Pivot.extremePrice`） | #130 / #131「値幅は高安」 |

この組み合わせの帰結として、**「高値は山1 と同水準、終値はネックライン」という足がそのまま
山2 になる**。`levelSpreadMetrics` の docstring が言うとおり分子（終値）と分母（高安）で基準が
違うので、`spreadRatio` に構造上の天井が無いのと同じ性質がここにも出ている。

### 3-2. 発端の形

issue #245 本文の実例。`btc_jpy` / `1hour` / 2026-09-04（実データ D の `limit=72` 窓 =
`BTC_JPY_1HOUR_2026_09_05_ISSUE_WINDOW`。窓の中の相対 idx で書く）:

| 役割 | idx | UTC | 終値 | 高安 |
|---|---:|---|---:|---:|
| 山1 | 41 | 2026-09-03T21:00Z | 12,718,980 | 12,807,555 |
| 谷（ネックライン） | 46 | 2026-09-04T02:00Z | 12,617,594 | 12,588,132 |
| **山2** | **50** | **2026-09-04T06:00Z** | **12,639,245** | **12,800,000** |
| 再上昇の H ピボット | 55 | 2026-09-04T11:00Z | 12,711,037 | 12,731,234 |
| ブレイク確認 | 56 | 2026-09-04T12:00Z | 12,396,727 | |

山2 は上ヒゲ 160,755 円の足で、終値はネックラインの **+21,651 円（0.17%）**しか上に無い。
`heightAbs` = 12,807,555 − 12,588,132 = **219,423** なので、

- `closeGap` = 21,651 / 219,423 = **0.099**（終値で見た山の高さは、パターン高さの 1 割）
- `wickShare` = 160,755 / 219,423 = **0.733**（ヒゲがパターン高さの 7 割）

### 3-3. この形は #242 で既に落ちている

山2（idx 50）の後に再上昇して H ピボット（idx 55）を作ってから割っているので、#242 の
経路ゲートが `peak_after_last_pivot` で `invalid` にする。**issue #245 の「順序」節が
「単独で問題になる事例を集めてから着手する」と書いているのはこのため。**

したがって残る問いは 1 つだけ:

> **「ヒゲだけの山2（谷2）の直後に、再上昇せずそのまま割る形」が accepted に混ざるか。**
> **混ざるならそれは正当な failed retest か、呼べない形か。**

この形は経路ゲートでは落ちない——山2 とブレイクの間にピボットが無いので
`detectPivotBeforeBreakout` が発火しない。落ちるとしたら同水準判定だが、そちらは終値基準
（`isSameLevel(a.price, c.price, DOUBLE_LEVEL_MAX_PCT)`）なので、**山2 の終値がネックラインの
すぐ上にあっても山1 の終値と 3% 以内なら通る。**

### 3-4. 量の定義

`pivots = [a, b, c]`（`c` が山2 / 谷2）、`heightAbs` は
`levelSpreadMetrics([a, c], [a, b, c]).heightAbs`（高安基準）。

| 量 | top | bottom | 読み |
|---|---|---|---|
| `closeGap` | `(c.price − b.price) / heightAbs` | `(b.price − c.price) / heightAbs` | 山2 の**終値**がネックラインからパターン高さの何割離れているか。**0 に近いほど「終値では山が無い」** |
| `wickShare` | `(c.extremePrice − c.price) / heightAbs` | `(c.price − c.extremePrice) / heightAbs` | 山2 のヒゲがパターン高さの何割か |

分子は終値と高安の**差**、分母は高安。混合基準そのものを 2 つの無次元スカラーに写している。
ネックラインは `necklineAt(neckline, c.idx)`（#211 のクランプ済み）——double / triple は
水平スカラーなのでクランプは恒等で、H&S だけが実際に線として評価される。

## 4. 分布（計測仕様 1）

数字は §10 §1 が単一ソース。ここは読み方だけを足す。

### 4-1. 全体

accepted な double は **延べ 1,151 / 実体 30 / 値動き 19**
（`completed` 延べ 257 / `near_completion` 延べ 894）。

値動き単位の分布は `closeGap` が min 0.030 / p50 0.415 / max 0.741、
`wickShare` が min 0.072 / p50 0.232 / max 0.733。

`near_completion` が延べで `completed` の 3.5 倍（894 対 257）あるのは主にローリング窓の効果——
未ブレイク構造は窓を 1 本ずつ伸ばすあいだ何度も出るが、ブレイクした瞬間に `completed` へ移る。
**値動きで見れば 14 対 6**（1 つの値動きが窓によって両方の status で出るので合計は 19 を超える）で、
延べの倍率よりは差が小さい。

### 4-2. side の非対称

| side | `closeGap` min | `wickShare` max |
|---|---:|---:|
| top | **0.030** | **0.733** |
| bottom | 0.241 | 0.400 |

**bottom には「終値では谷が無い」形が 1 つも無い**（min 0.241）。標本が 9 値動きしか無いので
構造的な非対称だと言い切れないが、**本 issue の症状は現行コーパスでは top 側にしか出ていない。**
Phase 2 で減点軸を足すなら、**bottom 側でも同じ量が意味を持つかは別に確かめる必要がある**
（式は符号反転で対称なので、実装上は両側に入る）。

### 4-3. 時間足別

`1hour` が延べ 701 / 実体 12、`1day` が延べ 40 / 実体 2、`4hour` は 0（§1 の注意のとおり
実 4 時間足の系列が無いので構造的に 0）。`closeGap` の下端 0.030 は `1hour` 側にあり、
`1day` の下端は 0.241。**ヒゲだけの山2 は短い時間足に出る**という向きだが、
`1day` の母集団が 2 値動きしか無いので比較にならない。

### 4-4. 母集団別

**標準コーパス（合成 704 + 実データ A）側は `closeGap` の下端が 0.241。**
`closeGap` ≤ 0.2 の形は**すべて実データ B / C / D のローリング窓**から出ている
（3 系列とも下端 0.030）。固定窓の 4 母集団では、実データ B に accepted double が
**1 件も無く**、C / D は**発端の形だけ**（延べ 24 / 8、実体 1、`closeGap` 0.099）。

**この偏りそのものが本 Phase の観測の 1 つ。** `closeGap` の小さい形は
**窓を 1 本ずつ動かして初めて見える**——固定窓 4 母集団（合計 1,088 ケース）では
発端の形以外に 1 つも出ない。理由は 2 つある。ローリング窓が固定窓の 10 倍のケース数
（11,016 対 1,088）を持つことに加えて、**窓の終端 `swingDepth` 本の余白**が
経路上のピボットを隠すので（§5-1）、**終端付近に山2 がある形ほど経路ゲートを通り抜けやすい。**

### 4-5. 空白帯（#214 の基準）

値動き単位の最も広い空白帯:

| 量 | 空白帯 | 幅 | 全幅比 | 根拠に使えるか |
|---|---|---:|---:|---|
| `closeGap` | 0.415 〜 0.538 | 0.123 | 17.4% | **いいえ**（値動き 19 < 30） |
| `wickShare` | 0.544 〜 0.733 | 0.189 | 28.5% | **いいえ**（同上） |

**帯は「ある」が、仮の閾値（0.2 / 0.5）の位置には無い。** そして値動きが 19 しか無いので、
**帯の広さは分布の谷ではなく標本の粗さを写している**（隣接差が大きいのは標本が疎なせい）。
スクリプトは `GAP_MIN_SAMPLES = 30` でこの判定を機械化してあり、実体行・延べ行は
「同じ値動きを重複して数えている」ので「重複あり（判断は値動き行で）」と出す。

**したがって #214 の基準では 0.2 / 0.5 の非恣意性を主張しない。** 帯の中へ動かした場合の該当:

| 動かす閾値 | 帯の中の値 | もう一方は据え置き | 該当（値動き） |
|---|---|---|---:|
| `closeGap` | 0.415 〜 0.538 の間 | `wickShare` ≥ 0.5 | **2**（発端の形 + 実データ C の 174-177-184） |
| `wickShare` | 0.544 〜 0.733 の間 | `closeGap` ≤ 0.2 | **1**（発端の形のみ。現状と同じ） |

**どちらに動かしても結論は変わらない**——増える 1 件も #242 系の形（§2 の 4）。

### 5-1. その後（ローリング窓での追跡）

構造キーごとの status 履歴（§10 §2 が verbatim）。**「最初に accepted になった窓」から
終端を 1 本ずつ伸ばしたときの status 遷移**:

| 系列 / `swingDepth` | 構成点 idx | 最初の accepted | その後 |
|---|---|---:|---|
| D / 2 | 329-334-338 | end=340 | `completed`×1 / `near_completion`×3 / **`invalid`×20**（最終 `invalid`） |
| D / 3 | 329-334-338 | end=341 | `completed`×2 / `near_completion`×2 / **`invalid`×19**（最終 `invalid`） |

| **D / 6** | 329-334-338 | end=344 | **`completed`×20**（最終 `completed`） |

2. **実データ D の `swingDepth: 2 / 3 / auto` は窓を伸ばすと `invalid` に落ちる。**

   **経路ゲートは意図どおり働いている。**
3. **実データ C の `swingDepth: 3 / auto` は最後まで `completed` のまま。** これは
   **窓の端の効果**で、`detectSwingPoints` が `for (let i = swingDepth; i < candles.length - swingDepth; i++)`
   なので、365 本窓（終端 idx 364）では idx 362 以降が極値になれない。再上昇の足は

どちらも `scoreComponents` の減点軸では変わらない。

## 6. 目視判定（計測仕様 3）

### 6-1. 判定の基準

**チャート画像を見なくても §5 と §10 の数値だけで検算できるように書いてある**（#262 §8-2 と同じ流儀）。
根拠に使った量は「構成点の終値・極値」と「区間の終値」の 2 種類だけで、どちらも凍結フィクスチャから
直接読める（検出器も閾値も通さない）。**独自の描画コードは書いていない**（`.claude/rules/charting.md`）。

順に当てて、最初に当たったものを採る:

1. **山2 の高値が山1 の水準に届いていない**（`isSameLevel(山1.extremePrice, 山2.extremePrice,
   DOUBLE_LEVEL_MAX_PCT = 0.03)` が偽。ヒゲ込みでも同水準でない） → **呼べない**
2. **割った後すぐ戻している**（ブレイク足の翌足から 3 本以内に終値がネックライン水準へ復帰）
   → **呼べない**
3. **山2 の翌足以降で終値がネックラインを「直接」割っている** → **正当な failed retest**
4. それ以外 → **保留**（4a: 割る前に山2 の終値を越えて戻している / 4b: 走査終端まで割っていない）

ブレイク判定には検出器と同じ ±1.5% バッファを掛ける（写しの一致は §10 §0 で検算済み）。
走査終端は**代表の窓の終端**＝検出器が見た情報だけ。参考として系列の末尾まで先読みした判定も
併記してあるが、**先読みは検出器に見えない情報**なので決定の根拠にはしない。

### 6-2. 「直接割った」を何で測るか（issue の基準からの読み替え）

issue #245 の判定基準は「その足の翌足以降で終値がネックラインを割っている（**#242 のゲートで
見た「直接割った」形**）」と書かれている。#242 のゲート本体（`detectPivotBeforeBreakout`）は
**ピボット列**を入力に取るので `swingDepth` に依存し、**その深さ依存自体が #251 案 3 で
仕様として固定されている**。目視判定の基準にそのまま使うと「同じ値動きが深さによって
別の判定になる」ことになり、3 値判定の意味が壊れる。

そこで本判定は**深さに依らない素の量**で「直接」を測る:

> **山2 の翌足からブレイク足の直前までの終値の最高値（bottom は最安値）が、山2 の終値を
> 越えていないこと。**

越えていれば「山2 を作った後にいったん山2 より高く引けてから割った」＝ #242 が
`peak_after_last_pivot` で落としたのと同じ値動きなので、**failed retest とは呼べず保留**にする。
使う量は構成点の終値と区間の終値だけで、ピボット列も閾値も通さない。

### 推奨（Phase 2 の入口。決定ではない）

**案 B を本命、案 A は採らない、案 C は「#245 としては閉じる」の形で併せて採る。**

理由:

1. **案 A の費用対効果が合わない。** 現行コーパスで効くのは 1 値動きで、それは #242 が

   `globalDedup` の代表が入れ替わる副作用があり（#142 / #204 で実測済みの経路）、

2. **案 B は `data.patterns` を動かさずに症状そのものを解消する。** issue #245 の症状は
   「終値で見ると山が存在しないのに山2 として報告される」であって、
   **報告が悪いのではなく報告に情報が足りない。** `content[0].text` が LLM への唯一の
   チャネル（`.claude/rules/tools.md`）なので、そこに `closeGap` を出せば LLM が
   「ヒゲだけの山だ」と読める。**閾値を持たず常に値を出す形なら #214 の基準に触れない。**
3. **「再上昇せずそのまま割る形」が 0 件だったことは #245 の前提を否定している。**
   issue の「順序」節は「単独で問題になる事例を集めてから着手する」と書いており、
   **集めた結果 0 件だった。** hard reject も減点も要らない、という結論に到達できる。
4. **窓の端の余白は別 issue にする。** §2 の 3 の（b）は #245 の対象ではないが、
   「同じ形が窓の長さで `completed` / `invalid` に分かれる」という観測可能な帰結を持つ。
   #251 が固定した深さ依存と同じクラスの話なので、そちらに寄せて扱うのが自然。

**決定はしない。** 案 B を採るなら、注記の文言・出す view・上位集合規約（`.claude/rules/tools.md`
規約 3 / 5）への影響を Phase 2 の入口で確定させること。

#### 1-5. 空白帯（閾値の非恣意性を主張できるか。#214 の基準）

### 5. 既存ゲートとの重なり

§2 の該当実体のうち、`validateLevelDiff`（高さ相対 0.5 = `MAX_LEVEL_SPREAD_RATIO` 0.5）や `validateMainPointsNecklineSide`（主構成点がネックラインの正しい側にあるか）で**既に落ちているもの**が無いことを確認する。**accepted を母集団にしているので 0 のはず**で、0 でなければ `near_completion` のゲート集合が完成済みと同じでない（#270）ということになる。

| 対象 | n | `validateLevelDiff` が理由を返す | ネックライン側検査が理由を返す |
|---|---:|---:|---:|
| accepted double 全部（延べ） | 1151 | 0 | 0 |
| accepted double / `completed` | 257 | 0 | 0 |
| accepted double / `near_completion` | 894 | 0 | 0 |
| §2 の該当（延べ） | 85 | 0 | 0 |
| accepted triple（延べ） | 6105 | 0 | 0 |
| accepted H&S（延べ） | 13792 | 0 | 0 |

**`closeGap` > 0 は `validateMainPointsNecklineSide` の帰結**——あのゲートは top で `necklinePrice − 山.price >= 0` を落とすので、`closeGap` = 0 以下の候補は accepted に入れない。したがって「終値では山が完全に無い（ネックラインと同値か下）」形は既に弾かれている。残っているのは**わずかに上**の帯で、その厚みが §1 の `closeGap` の下側の分布そのもの。

accepted double の `spreadRatio`（`validateLevelDiff` が見る量）: max 0.488（閾値 0.5）。H&S の肩の同水準上限は `HS_SHOULDER_MAX_PCT` = 0.05。
