# H&S confidence の多軸化（issue #204 Phase 2・実測ログ）

`detect_hs.ts` の完成済み 4 経路が共有していた `base = (tolMargin + symmetry + per) / 3` から
**`tolMargin` を捨て**、H&S 固有の 2 軸（`headProminence` / `timeSymmetry`）と
double / triple と共有する 2 軸（`retracement` / `breakoutQuality`）を足した。
[issue #204](https://github.com/tjackiet/bitbank-lab-mcp/issues/204) の
[Phase 2 方針コメント](https://github.com/tjackiet/bitbank-lab-mcp/issues/204#issuecomment-5502768865)
に沿った実装ログ。

Phase 1（PR #205、`hs-confidence-distribution-phase1.md`）の実測が前提。

## 変更の要旨

| | 旧 | 新 |
|---|---|---|
| 式 | `(tolMargin + symmetry + per) / 3` | 算出できた軸の相加平均（6 軸） |
| 同水準の軸 | `tolMargin`（正規化）と `symmetry`（生）の**両方**——同じ `relDev(左肩, 右肩)` 由来 | **`symmetry` のみ**（`tolMargin` を削除） |
| 足した軸 | — | `headProminence`（頭の突出ゲートに対する余裕）/ `timeSymmetry`（左右のバー数比）/ `retracement`（構造ゲートの戻り率）/ `breakoutQuality`（突破幅 ÷ パターン高さ） |
| `scoreComponents` | **付いていなかった**（H&S は 1 件も出していない） | 6 軸すべてを出す |
| confidence の算出位置 | 構造ゲートの直後 | **ブレイク検出と高さ算出の後**（`breakoutQuality` / `patternHeight` が要る） |

**doubles の解法をそのまま適用した**（`buildDoubleScore`。`symmetry` を残して `tolMargin` を捨てる）。
issue #199 の triple が逆の選択（`levelMargin` を残す）になったのは triple の `tolMargin` が
3 ペアの relDev 平均で中間点の情報を持つためで、**H&S は主構成点が 2 点（両肩）しか無く
その事情が無い**。`symmetry` は既存フィールドをそのまま使い、新フィールドは
H&S 固有の 2 軸だけを足した。

## 変えなかったもの（明示）

- **`finalizeConf` の H&S 係数 1.1 は変えていない。** 軸構成が変われば 1.1 の根拠も変わるが、
  係数と軸構成を同時に動かすと切り分けできない。再検討が要るなら別 issue を立てること。
- **relaxed 経路の `× 0.95` ペナルティも変えていない。** 理由は同じ。
- **`duration`（`periodScoreDays`）はそのまま。** triple（#203）では 109/109 が 0.6 の定数だったが、
  **H&S では 0.6 / 0.7 / 0.8 / 0.9 の 4 値すべてが出る生きた軸**（Phase 1 訂正 1）。
  #199 候補 2（バー数基準への置き換え）を H&S に横展開してはいけない。時間足間で意味が揃って
  いない問題は残るので、別途評価が要る。
- **`MIN_CONFIDENCE.head_and_shoulders` / `inverse_head_and_shoulders` は配線していない**（#206）。
  現在どの検出器も読んでいないので「再検証の対象が存在しない」。本 PR でも配線しない。
- **形成中（`forming`）経路は対象外。** confidence が別式
  （`min(1, max(0, 0.6×closeness + 0.4×progress)) × (暫定右肩なら 0.9)`）で、issue が扱う
  4 経路に含まれない。実測でも forming の構造は前後で全件不変。
- **#211（`necklineAt` の外挿クランプ）とは併走していない。** #211 案 B はブレイク検出を変えて
  `breakoutIdx` → `status` → `per` → `confidence` と連鎖するため、本 PR の効果と混ざる。

## 1. 軸の選定 — ネイティブ 89 構造を基準にした

Phase 1 は候補を 5 つ挙げていた。**#205 の結論 5 はプールした 857 構造の相関で順位を付けていたが、
自ら定めた錨（ネイティブ）を適用すると順位が変わる**（issue のコメントの指摘どおり）。
`r(rd)` が大きい軸は「confidence と相関している」ように見えても中身が rd の再掲なので、
両方を見る。

| 軸 | `r(rd)` 全体 | `r(rd)` ネイティブ | 分散（ネイティブ） | 判断 |
|---|---:|---:|---|---|
| (a) 頭の突出率 / `headProminencePct` | −0.02 | **−0.166** | 比 1.011〜4.306（中央値 1.639） | **採用** |
| (c) 時間対称性 `min/max` | −0.22 | −0.415 | 0.0642〜0.9730 | **採用**（限界は下記） |
| (d) `retracementRatio` | 0.01 | 0.339 | 0.2076〜0.8963 | **採用**（スコア換算後は `r(rd)` = 0.03） |
| (b) ネックライン水平度 | 0.66 | **0.725** | 0.0002〜0.0462 | **不採用**（rd の再掲） |
| (e) ブレイク品質 | −0.27 | −0.053 | 算出可 41.8% / 飽和 69% | **再計測して採用**（[1-2](#1-2-e-ブレイク品質は測り直した--飽和が-69--441-に下がる)） |

### 1-1. (d) は「スコアに換算すると rd と直交する」

Phase 1 が心配した「ネイティブでは `r(rd) = 0.339` に上がる」は**生の `retracementRatio` の話**で、
実際に軸として使うのは `retracementScore`（許容帯 [0.2, 0.9] の**中央で 1・端で 0**）。
帯を折り返す変換なので相関が消える:

| | 全体 857 | ネイティブ 89 |
|---|---:|---:|
| 生の `retracementRatio` の `r(rd)` | 0.012 | **0.339** |
| `retracementScore` の `r(rd)` | −0.16 | **0.03** |

**#205 が「プール時の打ち消しの可能性」と留保した点は、打ち消しではなく変換の効果**だった。

### 1-2. (e) ブレイク品質は測り直した — 飽和が 69% → 44.1% に下がる

**#205 の (e) の測定は古い。** #205 は
`patternHeight = |頭の price − **ブレイク足時点の**ネックライン|` で計算しており、
これは #208 の欠陥そのもの（`necklineAt` の外挿距離ぶん高さが歪む）で、PR #209 が
「頭の真下で測る」に直した後の値ではない。

`necklineProjectionHeight`（`nlAt(headIdx)` 基準。`breakoutTarget` が使うのと同じ高さ）で
測り直した結果:

| | 旧（ブレイク足時点の高さ） | 新（頭の真下の高さ） |
|---|---:|---:|
| 算出可（全体 857 構造） | 358（41.8%） | **358（41.8%。不変）** |
| うち 1.0 に飽和（全体） | 247（**69.0%**） | **158（44.1%）** |
| 算出可（ネイティブ 89） | 34（38.2%） | 34（38.2%。不変） |
| うち 1.0 に飽和（ネイティブ） | 21（**61.8%**） | **8（23.5%）** |

十分位（ネイティブ 34 件）:

```text
旧: 0.343 0.358 0.610 0.613 1.000 1.000 1.000 1.000 1.000 1.000 1.000
新: 0.502 0.502 0.510 0.526 0.577 0.691 0.789 0.789 1.000 1.000 1.000
```

高さそのものの比（新 ÷ 旧）は全体で中央値 1.311 / p75 **2.338** / 最大 149.3、
ネイティブで中央値 1.102 / p75 2.184 / 最大 3.372。**#208 が実データ B の 1hour ケースで
報告した「2.34 倍」は p75 に一致する。**

**「41.8% しか算出できず 69% が飽和」という #205 の結論は修正前の高さで測った値**で、
飽和は半分以下に落ちる。算出可の 41.8% は `near_completion` が未ブレイクである以上
原理的に上げられないが、`averageDefinedAxes` が欠測を平均から外すので減点にはならない。
**採用する。**

ただし限界を 2 つ記録しておく:

- **新しい高さで測ると rd との相関が上がる**（全体 −0.27 → **−0.454**、ネイティブ
  −0.053 → **−0.499**）。飽和が減って値が動くようになったぶん、rd との共変が見えるように
  なった、という読みが自然。(b) を落とした基準（ネイティブ 0.725）よりは弱いが無相関ではない。
- 算出可の 358 件で `retracement` と **−0.62**（ネイティブ −0.76）の負相関がある。
  2 軸は独立ではない。

### 1-3. (c) 時間対称性は採るが、rd との相関を隠さない

(c) は**候補の中で最も分散が広く**（ネイティブ 0.0642〜0.9730）、**現在どこにも使われていない量**で、
教科書的な H&S の要件（左右の脚の釣り合い）そのもの。一方で `r(rd)` はネイティブで −0.415 あり、
「長く伸びた構造ほど肩の水準がずれる」という機構的な共変がある。

合成した confidence の `r(rd)` で見ると、(c) を足すと独立性は下がる:

| 軸構成 | `r(conf, rd)` 全体 | ネイティブ | 実測 sd（ネイティブ） |
|---|---:|---:|---:|
| 旧（`tolMargin` + `symmetry` + `per`） | **−0.913** | **−0.955** | 0.088 |
| doubles そのまま（`sym` + `ret` + `bq` + `dur`） | −0.028 | −0.113 | 0.107 |
| + (a) 突出 | −0.045 | −0.179 | 0.106 |
| **+ (a) 突出 + (c) 時間対称（採用）** | −0.156 | **−0.344** | **0.115** |

**それでも (c) を採る。** rd との相関を最小化することは目的ではない——`symmetry` 自体が
定義上 rd そのものなので、composite が rd とまったく無相関になるほうがむしろ不自然。
落とす基準は「rd の情報を重ねるだけか」で、(b) の 0.725 は再掲だが (c) の 0.415 は
分散の 83% が rd で説明できないという意味になる。**判別力（sd）は (c) を足したほうが高い。**

### 1-4. 軸の定義

| 軸 | 定義 | 備考 |
|---|---|---|
| `symmetry` | `clamp01(1 − relDev(左肩, 右肩))` | **既存フィールド**（double と共有）。正規化していない生の relDev |
| `headProminence` | `clamp01(1 − ゲート ÷ 実測突出率)` | **新設。** 実測突出率は検出側のゲートと同じ式（`頭 ÷ max(肩) − 1`、逆 H&S は `1 − 頭 ÷ min(肩)`）。ゲートちょうどで 0、2 倍で 0.5、∞ で 1。relaxed は `headProminencePct × factors.head` |
| `timeSymmetry` | `min(左肩→頭, 頭→右肩) ÷ max(同)`（バー数） | **新設。** 1 = 左右同じ長さ |
| `retracement` | `retracementScore(gate.retracementRatio)` | `patterns/scoring.ts`（#207 で切り出し済み）。double / triple と同一 |
| `breakoutQuality` | `breakoutQualityScore(nlAt(breakoutIdx), 突破足の終値, necklineProjectionHeight(...), side)` | 同上。**高さは `breakoutTarget` と同じ「頭の真下」基準**（#208 / #209） |
| `duration` | `periodScoreDays(structureRange)` | **変更なし** |

上限が無い量（突出率の比は実測で最大 32 倍）を `1 − ゲート ÷ 実測` に畳んだのは、
`marginFromRelDev` が上限ゲートに対して `1 − 実測 ÷ 上限` を取るのと同じ発想の**下限ゲート版**で、
任意の飽和定数（「比 3 で 1 とする」等）を置かずに済むため。

**共有ヘルパの追加切り出しは無い。** `retracementScore` / `breakoutQualityScore` /
`averageDefinedAxes` は #207 で `tools/patterns/scoring.ts` に切り出し済みで、そのまま使った。
`headProminenceScore` / `timeSymmetryScore` は H&S 固有なので `detect_hs.ts` に置いた
（他の検出器に対応する概念が無い）。

### 3-2. 件数が動いた — issue の想定と違うので原因を書く

issue はこう書いていた:

> **H&S には confidence のゲートが無い**ので、confidence を変えてもパターンが増減する経路は無い。
> → **type 別件数の不変**を確認し（…）件数が動いたら想定外なので原因を説明する。

**検出器層では想定どおり完全に不変**（[2 章](#2-検出器層--件数は完全に不変)）。
**出力層では 940 ケース中 6 ケースで H&S の件数が動いた**（延べ +6）:

| ケース | 系列 / tf / `swingDepth` | before → after |
|---|---|---|
| `B:1hour:d2:f1c1i0` / `f1c1i1` | 実データ B / `1hour` / 2 | 5 → **6** |
| `B:1hour:d2:f1c0i0` / `f1c0i1` | 実データ B / `1hour` / 2 | 0 → **1** |
| `sweepB:5min:dauto` / `d2` | 実データ B / `5min` | 7 → **8** |

**原因は `globalDedup` の代表選択で、confidence のゲートではない。**
`globalDedup`（`helpers.ts`）は期間の重なり率が 70% 以上の候補を 1 つに畳み、勝者を
`statusScore` → **`confidence`** → `range.end` の新しさで選ぶ。ここで注意すべきなのは
**畳み込みが逐次（greedy）**だという点——`out` に既に入った代表と次の候補を突き合わせるので、
**代表が変わると `range` が変わり、その後の重なり判定の結果まで変わる**。

`B:1hour:d2:f1c0i0`（`includeForming: true` / `includeCompleted: false`）の実例:

- before: H&S 系は 0 件。
- after: `inverse_head_and_shoulders` 242-245-249-294-305（`near_completion`、confidence 0.50）が 1 件残る。

この構造は before では、期間の重なる `completed` の逆 H&S に `statusScore` で負けて畳まれ、
その勝者が `includeCompleted: false` のライフサイクル絞り込みで落ちていた（＝ 0 件）。
after では畳み込みの相手が別の代表に変わり、この `near_completion` が別グループとして
残ったため出力に出る。

**「confidence を変えると出力の件数が動きうる」は H&S に限らず `globalDedup` を通る
すべての type に共通する性質**で、#199（triple）では confidence が下がって
`MIN_CONFIDENCE` に切られる効果に埋もれていた。ここでは切る経路が無いぶん、
dedup の性質だけが単独で観測できている。

## 5. relaxed 経路 — 実装は直したが**効果は測れていない**

relaxed の 2 経路も strict と同じ 6 軸に直し、`headProminence` のゲートだけは
経路の閾値（`headProminencePct × factors.head`）を渡すようにした
（strict の `tolerancePct` / relaxed の `tolerancePct × factors.shoulder` と同じ扱い）。

**ただし本コーパスでは relaxed は 940 ケースで 1 件も accept していない**
（before / after とも `_fallback` を持つパターンが 0 件）。#205 の実測と同じ状況で、
**relaxed 固有の式（`× 0.95` ペナルティ、段の係数を掛けた閾値）は一度も実行されていない。**

したがって relaxed について本 PR が言えるのは:

- **「変化なし」ではない。「測れなかった」。** コーパスで実行されない経路の挙動は、
  実測では前後どちらも空集合で、差分が 0 であることに情報が無い。
- 代わりに**ユニットテストで固定した**（`tests/patterns/detect_hs.test.ts` の
  「relaxed 経路も同じ軸構成で、突出ゲートは段の係数を掛けた値になる」）。
  肩 100 / 105 で strict を落として relaxed 第 1 段（`shoulder ×1.6` / `head ×0.6`）に
  落ちる入力を使い、`headProminence` が `1 − 0.024 / 0.238095` になること（strict の
  ゲート 0.04 で測った値とは**違う**こと）を数値で固定している。
- 「relaxed H&S は事実上デッドコードではないか」という問い（#205 のコメント）は
  **本 PR でも解けていない。** スコープ外。

## 6. スキーマ / 型の宣言

新設した 2 軸は TS と Zod の**両方**に宣言した（#155 / #160 / #184 / #189 の 4 回に加え、
さらに #199 でも起きた「Zod 未宣言で `parse()` が黙って strip」を 6 回目にしないため）:

- `tools/patterns/types.ts` の `PatternScoreBreakdown` に `headProminence` / `timeSymmetry`
- `src/schema/patterns.ts` の `DetectedPatternSchema.scoreComponents` に同 2 フィールド

**`symmetry` の意味は差し替えていない。** 既存の description が
「2 つの構成点（谷-谷 / 山-山）の同水準度。**double 系のみ**」だったのを
「2 つの主構成点（谷-谷 / 山-山 / **左肩-右肩**）の同水準度。**double 系と H&S 系**」に
直しただけで、量そのものは double と同じ `1 − relDev(2 点)`。
`.claude/rules/tools.md` 規約 7 が禁じているのは「同じ語の意味を差し替える」ことで、
**同じ意味の量を出す型が増えるのは対象外**。

機械的な固定は `tests/detect_patterns_meta_schema_parity.test.ts` の
`DATA_PARITY_FIXTURES`（`noisy` 側）の `requiredKeys` に 6 軸すべてを追加した。
`_fallback`（#189）/ `levelMargin`（#199）と同じ「フィクスチャがその経路を踏んでいないと
宣言漏れを検出できない」穴があるため、**`noisy` フィクスチャが 6 軸すべてを埋めることを
先にアサートする**形にしてある（実測値は `symmetry` 0.9859 / `headProminence` 0.6893 /
`timeSymmetry` 0.7143 / `retracement` 0.0361 / `breakoutQuality` 0.1402 / `duration` 0.7）。

宣言を外すとテストが落ちることも確認済み（`headProminence` を Zod から削って
`patterns[].scoreComponents.headProminence` の strip を検出させた）。

持つ 2 件を**名指し**で拾っていた。だがその 2 件は「分母が潰れた構造」の全体ではなく
**`globalDedup` の勝者**で、confidence の式が変われば別の構造が代表になる。
実際に本 PR で、分母が潰れた 4 構造はいずれも代表を取れなくなり `data.patterns` から 0 件になった。

issue #210 が守りたいのは「退化した分母では進捗を出さない」であって「その構造が dedup に勝つ」では
ないので、**対象を dedup より手前の検出器出力に移した**（4 構造すべてを idx 付きで固定）。
`detectPatterns` 側には「ブレイク済み H&S は、進捗を出すか理由を申告するかのどちらか」という
**どの構造が勝つかに依存しない**不変条件を別に置いた。#199 が
`level-spread-triple.test.ts` の順序依存を名指しに直したのと同じクラスの修正。
